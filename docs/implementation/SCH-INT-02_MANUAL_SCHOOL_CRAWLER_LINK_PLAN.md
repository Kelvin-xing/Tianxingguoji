## 1. 业务结果与决策边界

建议保留人工建档原始记录，以同一个 School 内部 UUID 增加经人工核对、Founder 审批的来源关联及抓取目标。没有爬虫来源编号的学校，也可以先建立稳定抓取目标，依批准的入口执行单校抓取；以后发现爬虫来源编号时，再核对并追加对应关系。无需重建 School、伪造爬虫快照或改写最初的人工记录。

“客户手动添加”在本稿中指天星教育内部获授权人员建档，不新增学生、家长等外部客户的学校维护入口。沿用现有建档资格及试用授权边界，不重新分配角色。

本稿分清三件事：

1. **来源及身份对应可用**：人工核对已保存，抓取入口已批准，技术适配器支持该入口。
2. **可以发起任务**：目前只依据已确认 BR 支持有页面访问权用户发起单校任务。来源可用不自动产生任务。
3. **资料生效**：任务结果先成为候选，由有权用户另行启用，来源审批或抓取成功均不代替资料启用。

未来自动/定时抓取应消费同一份已批准目标集合，不因学校最初由人工还是爬虫发现而区别对待。但无人触发、首次全量/批量种子导入均未获 BR 确认。本稿不安排这两项的实施步骤：**此部分需要项目负责人先补充确认 BR，再进入实施**。单校关联方案不依赖首次全量导入获批；自动覆盖目标必须等待定时规则获批才能兑现。

## 3. 推荐模型：学校身份、来源关联、抓取入口分离

### 3.1 固定学校身份

`schools_schools.id` 是唯一学校身份。建档、来源核对、抓取、候选、启用和历史引用始终使用该 UUID。不用名称、教育局编号、网址、爬虫键或抓取目标编号替代它。

保留 `schools_provisional_records` 的原始内容、`status`、版本 1 及所有不可变保护，**不修改 schema 或触发器**。它回答“当时谁以什么内容建立了一条未验证学校记录”，不承担当前抓取配置或整个学校当前验证状态。新资料及配置各自追加版本；取得抓取资格不代表学校整体已验证，是否取消未验证标记需另有 BR，不能改写原行实现。

### 3.2 来源关联

建议另存 `(provider, external_school_key) → school_id` 的经确认对应关系，provider 表示来源命名空间，避免不同来源相同字符串键互相碰撞。该键只定位外部来源记录；爬虫换键、换域名不能改变 School UUID。

- **来源已有此校**：展示候选来源记录的中英文名、教育局编号、校址/学段、官网和资料页，与内部学校并列核对。人工明确确认对应同一学校，再进入来源审批；匹配分数、同名或同网址仅用于提示。
- **来源尚无此校**：提交已知入口及核对证据；审批通过后生成天星内部稳定 `target_id`，直接用批准配置发起单校任务。外部学校键可暂缺，不伪造教育局编号，也不要求先把全目录导入爬虫。
- **以后出现外部编号**：针对原 UUID/target 发起新增对应关系的核对申请，保存证据和决定；不创建第二所 School。若编号已关联另一 School，停止自动关联并进入人工治理，不抢占、不合并。

建议首次对应确认与来源审批在同一申请中完成，Founder 审批时分别确认“同一学校”和“允许采用这些入口”，提交者不能自审。首次对应确认人的具体权限、独立绑定键的提交权限及撤销/改绑规则列入第 7 节待确认，不能把普通爬虫启用权解释为绑定身份的权限。

### 3.3 抓取目标与入口

`target_id` 是执行任务用的稳定技术标识，关联 School UUID 及当前已批准来源配置版本；即使外部 registry 没有该校，也能下发该目标。配置中分别保存官网、学校资料页和招生资讯页，不能合成一个 website 字段；教育局编号等是核对信息，不能仅靠编号非空当作可抓取入口。

建议同一学校由一个统一目标协调任务，其下可有多个已批准入口；外部来源对应关系独立保存。每个有效 `(provider, external_school_key)` 至多关联一个 School；更复杂的多校址、多学段与多个外部记录的对应粒度须先确认，模糊情形保持待核对。

内部来源配置是抓取目标的权威来源，外部 crawler registry 是执行侧输入或投影，不能反向覆盖已批准配置。单校执行请求携带 School UUID、target、来源版本及关联版本，结果回传同样的对应信息；外部程序不创建 ERP 学校，也不直接写正式资料或自动启用。

手工目标与原生发现目标使用同一适配器契约，不以“必须存在静态 registry 行”作入口条件。如现有爬虫仅支持 registry 选校，后续另票提供显式单目标输入适配；在适配完成前显示执行不可用，不能冒称来源审批后已能实际抓取。本票未核实外部爬虫当前实现能力。

## 4. 人工确认与单校操作流程

| 步骤 | 用户动作与系统结果 | 边界 |
| --- | --- | --- |
| 1 建档 | 沿用最小名称要求生成 School UUID，保存原始 provisional | 不强制网址，不自动网络抓取，不降低现有权限检查 |
| 2 提交来源核对 | 在基础资料旁填写入口/辅助信息或选择外部候选；展示内部 UUID、双方名称/编号/页面/校址和不确定项 | 未知继续标未知；系统不猜测网站。提交资格按已确认范围校验，不据未知资料补充权限授予任意来源改绑权 |
| 3 待处理更新 | 展示关联及入口旧新值、证据、提交人、疑点、预期版本 | 没有快照也能读取学校原始建档与来源申请；不依赖现有 overlay 的活动快照外键 |
| 4 审批 | Founder 核对学校对应和抓取入口，批准或驳回并记理由；禁止自审 | 证据不足、共用域名、不同校址或编号冲突时提示人工核对；不能仅凭 URL 自动关联。无人能合法审批时保持待处理 |
| 5 获得来源可用状态 | 同一事务保存批准回执、关联修订和配置修订，更新当前投影 | 不启动网络任务，不自动验证整校，不启用普通学校字段 |
| 6 用户点更新资料 | 服务端校验页面访问、来源状态、可执行目标；同一 School 有进行中任务则复用 | 建议只有至少一个适配器支持的批准入口且身份无未决疑点时可新发起；此按钮条件仍需 BR 确认 |
| 7 查看及启用 | 回传结果经来源/身份校验后进入候选，逐项启用或全部接受 | 保留空值、失败、人工冲突及同字段并发保护；不自动启用 |

新来源待审批时不使用新入口。原批准版本若无疑点，建议继续保留原版本；一旦发现身份疑点，建议阻止新任务，并将相关候选置于待核对。配置或关联在任务期间改变时，保存原任务使用的版本和结果，不能把结果重标为新学校/新来源；是否允许旧候选继续启用须先补充规则，未确认前不放行该分支。

来源页面显示值与执行配置应明确关联但不得混淆：逐项接受、全部接受、恢复旧值若会改变执行入口，仍须来源审批；爬取出的证据链接不会自动升级为执行入口。来源申请中的名称/教育局编号是核对证据，不随来源批准静默覆盖学校业务字段。

## 5. 建议 schema 与兼容设计（逻辑结构，不是 DDL）

以下为可审阅的数据职责和约束建议；物理表名可在获批后的技术契约中冻结，不在本票创建表或迁移。

| 对象 | 建议字段/职责 | 不可变与关联约束 |
| --- | --- | --- |
| `schools_provisional_records` | 原样保留 | 不放入抓取入口；不改 UPDATE/DELETE/TRUNCATE 保护，不升 record_version |
| `schools_schools` | 保留 id、组织范围及现有可空 `source_school_key` | 保留旧列及不可变触发器，把旧列定位为历史接入键；新功能不写入、不以其非空作为资格条件 |
| 新增 `schools_source_change_requests` | id、school_id、organization_id、申请种类、预期关联/配置版本、来源键及入口旧新值、名称/教育局编号/校址核对证据、提交人/时间/理由 | 申请内容追加且不可改；更正提交新申请并引用前项。直接引用 School，不要求 crawler snapshot |
| 新增 `schools_source_review_receipts` | request_id、决定、审批人/时间/理由、明确对应确认及入口决定 | 追加式回执；一次申请一个最终决定，禁止自审；通过时与修订和审计原子提交 |
| 新增 `schools_source_link_revisions` | id、school_id、provider、external_school_key、前序修订、决定回执、版本、动作及时间 | 关联证据不可变。以当前投影约束一个有效来源键不属于两所 School；不把网址设为唯一身份键 |
| 新增 `schools_crawl_source_revisions` | id、school_id、各类入口列表、适配器标识、前序版本、批准回执、时间 | 只追加批准配置版本；每个入口有明确类型。源网址旧新值永久可追溯，派生候选不直接写这里 |
| 新增 `schools_crawl_targets`（当前投影） | target_id、school_id、organization_id、当前批准配置及关联版本引用、record_version | 建议每 School 一个目标；仅由批准事务推进指针，可由修订历史重建。目标存在不等于有调度授权；不增加默认 enabled 的自动计划 |
| 单校任务/候选契约扩展 | school_id、target_id、配置/关联版本、任务编号、发起人、实际抓取时间、结果、原始包引用/hash、字段来源证据 | 候选不能自行改绑定；进行中任务按 School 复用。成功、失败、无变化均追加历史；原始包/旧版本不改写 |

所有新对象保留服务端确定的单一组织上下文、RLS、同组织/同 School 的复合外键；当前指针必须引用本校已批准修订。审批事务锁定申请、学校及当前版本，并检查来源键冲突；同版本并发只允许一个成功，旧申请要求重新核对。幂等请求不重复建目标、修订、任务或审计。业务状态、必要审计及 outbox 同事务，任何失败全部回滚。

### 5.1 为什么不直接允许修改 source_school_key

允许 NULL → key 也只能存一个字符串，不能表达无外部键但有批准入口、多来源命名空间、网址版本、证据、审批与改绑历史；还需要放宽既有身份触发器。推荐新增关联机制，保留该列历史含义，不建立“旧列与新表双写”的第二套权威。

既有 snapshot record 上的来源键继续表示当时来源，不随新关联变化改写。历史键可作为已有学校来源核对的线索，但不能仅据旧键/旧快照自动赋予执行入口审批。已有学校若需接入新目标机制，也经同一核对流程。

### 5.2 无快照学校的有效资料与读取

来源审批独立于学校资料 overlay，可先为无快照学校完成；普通人工资料批准仍遵守 BR-051 的 overlay revision 语义。后续有效资料设计需支持“人工建档基线”与“爬虫记录基线”两类明确引用，而不是生成虚假的 crawler snapshot 满足外键。

建议对后续 overlay/有效版本契约增加互斥基线类型及引用：人工基线引用该校 provisional，爬虫基线引用该校不可变来源记录；配套纠正迁移再调整目前非空 snapshot 依赖及同校约束。保留旧版本/外键可追溯性，不改写已存在的 overlay、resolved revision 或申请固定引用。此处是 SCH-INT-01 单校有效版本设计的必要依赖，不以本票替代完整字段 schema 冻结。

首次抓取按本校 UUID 追加原始记录和候选，人工启用后生成本校新有效版本；不要切换组织级 active snapshot 来使单校生效，否则可能令未出现在该包中的其他学校消失。需要后续单校有效版本读取适配，不能仅凭新增来源表宣称闭环完成。

目录、详情及 Cases 读取需按 School UUID/有效版本判断可用，并按 UUID 消除人工记录与抓取资料的重复展示；原始 provisional 放在履历中保留。至少学校详情与来源申请可在无快照时访问。Cases 的既有主表来源键非空检查须纳入兼容评估，但本票不扩大未验证学校的选校/申请资格。

## 6. 必須保留的履历

| 履历 | 内容 |
| --- | --- |
| 原始建档 | 原学校 UUID、最小资料、未验证标记、创建人/时间、版本 1 |
| 身份核对 | 内外部标识、核对时名称/编号/校址/各类页面、证据、疑点、确认人/时间与结论；未知不能伪装已核实 |
| 来源治理 | 提交及审批人、旧新来源键和网址、预期/实际版本、理由、批准/驳回；未来如批准撤销或改绑，同样追加历史 |
| 抓取 | 发起人、任务复用关联、任务及 target 编号、固定的配置/关联版本、实际抓取时间、成功/失败/无变化、原因及原始包；检查时间不代替旧值采集时间 |
| 资料启用 | 启用人/时间、原始任务/来源、实际选择字段、逐字段旧新值、形成版本；全部接受跳过空值和人工冲突，显式采用冲突字段另记 |
| 恢复与并发拒绝 | 恢复引用的旧版本和生成的新版本；资料或来源已变化时的稳定冲突结果，不静默沿用过期确认 |

学校业务履历按权限展示核对内容，通用审计/outbox 仅记必要 ID、动作、版本、时间及履历引用，不复制自由文本、完整申请、姓名或敏感网址参数。已有学生申请引用的历史资料不随新抓取、关联变更或恢复改变。

## 7. 需要项目负责人新增/补充确认的 BR 清单

以下 D 编号只是本设计的讨论项，不是已确认 BR，也不在本文分配正式 BR 编号。确认后先更新需求模块及 CHANGELOG，再形成对应实施票。

| 讨论项 | 需要决定的业务问题 | 对本方案的依赖与停止条件 |
| --- | --- | --- |
| D1 首次来源对应与提交资格 | 谁可提交首次来源及纯外部键关联；是否接受由 Founder 在来源审批中同时确认学校对应；对应错误后的撤销/改绑资格、理由与效果 | 来源审批人和禁止自审已确认，不重复请求；首次身份对应的具体流程尚未冻结。该分支先确认后实施，不默认所有可抓取用户能改绑 |
| D2 单校抓取可用条件 | 是否接受至少一个可执行的批准入口、对应无疑点即可抓取，外部编号/教育局编号可缺；无入口/适配器不可用如何提示 | 影响手工学校第一次抓取；不能强制全部辅助字段齐全，也不能凭校名猜网址 |
| D3 身份疑点与来源变更中的任务 | 出现疑点是否暂停新任务；旧批准入口何时继续可用；改来源时已有任务和候选是否须重新核对/抓取 | 本稿建议保留证据并阻止不确定结果启用；具体恢复及旧候选采用规则未定，不自行实现完整状态机 |
| D4 校址、学段及对应粒度 | 一校多校址/多学段、一个外部记录包含多个实体时怎样人工判定；是否允许同校多个外部键 | 模糊情形停留待核对，不自动合并、拆分或重定向。复杂多对多映射不预建 |
| D5 首次全量/批量种子导入 | 是否允许、数据范围、来源审批与逐校身份核对、重复/不确定项处理、导入与资料启用的权限边界 | **此部分需要项目负责人先补充确认 BR，再进入实施**。本票不依赖、不执行、不编排批量导入；现有合成 seed 或历史 release 不构成授权 |
| D6 无人触发自动/定时抓取 | 是否允许；适用学校、启停责任人、频率/时间窗、执行身份、失败重试/暂停及人工任务重叠规则、是否需要通知 | **此部分需要项目负责人先补充确认 BR，再进入实施**。仅说明未来应消费同一批准目标集合；不确定频率、不建调度器、不预设全部学校自动加入。自动任务也不得自行启用结果 |
| D7 未验证学校状态与资格 | 获得来源/首次抓取/首次启用是否影响未验证标记及选校资格，分别需要什么确认 | 不是取得抓取资格的必需前提。本稿不自动转 verified、不扩大 Cases 权限；如期望这些效果需另票确认 |

权限设计还须核对 [BR-015](../../../txgj-doc/business-requirements/10-identity-access.zh-CN.md) 的试用授权与 BR-051 专项来源审批要求，不以旧代码中的 L1 普通变更审核能力自动扩大来源审批权。如有解释冲突，交负责人明确，不自行取权限并集。

对 D5/D6 的批准相互独立：批量种子导入批准不授权周期任务，周期任务批准也不授权批量建立或合并学校。“单校一次全部接受字段”不是批量学校更新；人工点击批量更新也不是无人调度。任何未决分支均不能从本设计标题或后续技术迁移推导已获批准。

## 8. 范围边界及后续审查条件

本票只做源码现状核实、推荐模型、schema 职责、流程/履历、待确认 BR 与边界说明。明确不做：

- 产品代码、API/DTO 实现、SQL/触发器修改、基线生成、数据修复、测试代码或爬虫 registry 修改。
- 首次全量/批量种子导入、批量更新、cron/自动调度、任务运行或真实学校资料启用。
- 按网址、名称或编号自动关联、合并、拆分、创建新学校或改派历史资料。
- 学校验证状态升级、Cases 资格扩张、新角色/外部客户入口、多组织功能。
- PR、合并 main、部署、云资源或任一数据库操作。2026-09-20 后续授权仅允许将本文提交并推送至独立分支，不构成实施授权。

获批后另行制定对应范围的实施与验收计划；本稿不列出 D5/D6 的开发排期或执行步骤。单校实现至少需在真实本地环境证明以下结果，当前均未运行：

| 审查场景 | 必须证明的结果 |
| --- | --- |
| 仅名称建档后补来源 | School UUID 不变、原始行仍版本 1；无需历史爬虫快照或全量种子即可提交审批 |
| 无外部键但有批准入口 | 支持该入口的适配器可以接受显式单目标；抓取结果回到原 School |
| 来源键已有归属、同网址多校、换域名 | 不自动关联/合并/重定向，显示人工核对原因并保存决定 |
| 未审批、无权限、自审、并发批准 | 无未批准入口被执行；稳定拒绝/冲突；业务、审计、幂等一起回滚 |
| 人工来源校与原生来源校 | 使用同一资格检查与单校任务机制，同校并发复用，无创建来源歧视 |
| 首次抓取及再次更新 | 原始记录与有效版本分离，字段选择及保护生效；不因单校包使其他学校消失 |
| 来源在任务期间变化 | 原版本和结果可追溯，不串到新 School/新配置；按批准后的 D3 处理 |
| 自动能力未获批准 | 没有无人任务、隐式定时加入或批量导入；来源审批不会启动调度 |
